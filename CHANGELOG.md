# Changelog

## Unreleased (0.20.13)

- CLI: `xiu --list-sessions` and `xiu --resume <id>` read the workspace's session logs only once the workspace is trusted, as `xiu report`, `xiu recover` and `xiu audit` already do for task records. Before, `--list-sessions` listed the sessions of an untrusted workspace (ids, models, first tasks) and exited 0, from a pipe too, and `--resume <id>` loaded the log before the trust question. Now a terminal asks the usual trust question first; a pipe counts the workspace as not trusted, prints the existing one-line explanation and exits 1 without reading the log; a `--json` run keeps its `not_started` result line. A trusted workspace, or `--trust-workspace`, behaves as before.
- CLI: an option or environment-variable value Xiu cannot accept is reported as the one-line usage error it is. `xiu --stall-timeout-seconds -1 "task"` used to print `Xiu could not start: The connection or response timed out.` with "Check network and proxy settings" as the next step, because the explanation catalog classified the message by its words ("timeout"). Option validation (`src/config.ts`), `--json` without a task, the provider-recovery option rules and `--language` now throw `UsageError`, which the catalog never classifies, so the output is `Error: stall-timeout-seconds must be a positive integer when provided` and nothing else; the `--json` result line is unchanged.
- CLI: `--cwd` pointing at a file or at a path that does not exist now stops every command but `xiu doctor` before trust, plugins or records are looked at, with the usual four lines (`Xiu could not start: The workspace path is a file, not a directory: <path>. …`, the next step, `xiu doctor`, and the raw message with the new `workspace/missing`, `workspace/not-directory` or `workspace/unreadable` code). Before, a task printed one bare `Error: Workspace does not exist: <path>` for a file as well as for a missing directory, and `xiu report runs`, `xiu recover` and `xiu audit` reported on the non-existent workspace ("no task run to report yet", or "not trusted"). The `--json` result line keeps the raw message (`Workspace does not exist: <path>`), so scripts that match on it are unaffected.
- CLI: closing the terminal window while a task runs now ends like Ctrl+C. The window's pty goes away, SIGHUP arrives (handled since the previous entry) and the next write to the terminal fails with `EIO`; that error was not one `src/broken-pipe.ts` recognised, so the status line's write inside the SIGHUP handling threw, the process died with exit 1 and the run stayed `running` in the journal. `EIO` now counts as a gone reader like `EPIPE`, and a broken output during a shutdown that is already under way no longer exits early, so the task is cancelled and its record closed. A plain (non-`--json`) one-shot task that stops after it started now reports `Task stopped: <reason>` with the one-shot exit code for its outcome instead of the startup heading `Xiu could not start: The operation was cancelled`.
- CLI: `SIGTERM` (`timeout 300 xiu --json "task"` running out of time, `kill`, a stopped container, a cancelled CI job) and `SIGHUP` (the terminal went away) are handled like Ctrl+C instead of ending the process at once: the running task, project check or task preparation is cancelled through the same `cancelActiveWork()`, the task-run journal records `cancelled` (before, the record stayed `running` and every later one-shot run reported an interrupted task until `xiu recover abandon`), a `--json` run still prints its final `result` line (`outcome: cancelled`, exit code 1), and an idle interactive session leaves the way `/exit` does with `Received SIGTERM; leaving Xiu.` on stderr. A second signal while that is in progress exits at once (143, or 129 for `SIGHUP`). `readInteractiveInput` gains `endsWithInput` so the idle prompt can take an abort signal without changing the piped-EOF rule.
- CLI: an interactive session whose stdin is a pipe (`printf '/mcp\n' | xiu`, a script feeding commands line by line) now ends when the input ends, the way `/exit` ends it: `Input ended; leaving Xiu.`, MCP servers closed, exit code 0. Before, the prompt waited for a line that could never come: with a connected MCP server the process never exited, and without one it vanished by draining the event loop, skipping the shutdown. `readInteractiveInput` rejects with `InputEndedError` when the piped input is over at an idle prompt; while a task runs it keeps draining the task's output until the task settles, so the end of the input never interrupts a task.
- CLI: a closed output pipe (`xiu report | head -1`, `xiu --json "task" | jq -c . | head -1`, a consumer that exited) no longer kills Xiu with `Unhandled 'error' event: write EPIPE` and a Node stack trace. `src/broken-pipe.ts` listens for `EPIPE` on stdout and stderr once at startup: with nothing running the process exits quietly with its current exit code; while a one-shot or interactive task, a project check or task preparation is running, the broken pipe cancels it exactly like Ctrl+C (`stopTask`, the abort controllers), says so once on stderr, lets the task-run journal record the end instead of leaving a `running` record that the next start would report as interrupted, and the queue's remaining tasks are not started. Other stream errors are still thrown.
- CLI: `--provider <id>` with an id that none of the configured profiles has (`xiu --provider nosuch "task"`, a typo of a profile id) now stops right after plugins load, before MCP servers, indexing or the model, with `Provider "nosuch" is not configured. Configured providers: fake. Pass one of those ids to --provider, or start xiu without --provider and add it with /provider add; this run did not start.` and exit 1 (`not_started` on the `--json` result line); an interactive start with such an id exits the same way instead of entering setup mode. With no profile configured at all the start still reaches the first-run wizard. Before, the run went on as "unconfigured" and failed at the model with "No Provider selected. Use /provider add to add one.." A plugin-provided profile can now be chosen with `--provider` (before, only the saved choice could name one). The one-shot "provider is not configured" message no longer ends with a doubled period. Tests: the message in both languages, and a real CLI run in plain, `--json` and interactive form that checks the exit code, the message and that no MCP connection or indexing started.
- CLI: a one-shot task that is a mistyped script command (`xiu doctr`, `xiu reprot json`, `xiu Doctor`: at most three words, the first one letter or a letter case away from `doctor`, `report`, `recover` or `audit`, the others that command's argument words) no longer goes through the trust prompt to the model as a task. It stops before trust, providers or the model with exit 1 and `Unknown command doctr. Did you mean xiu doctor? xiu doctor, xiu report, xiu recover and xiu audit run without an interactive session; this run did not start and nothing was sent to the model as a task. If it is task text, write it as a full sentence.` (`not_started` on the `--json` result line). Longer tasks and other words (`edit README`, `recovr abandon 1234`, `export json`) stay tasks; the exact words are handled by the commands as before. Tests: the detector and both languages' messages, and the real one-shot test runs `doctr` and `--json reprot json`.
- CLI security: the workspace trust question is no longer asked when there is no interactive terminal (piped stdin or stdout, CI). Before, a plain one-shot run (`xiu <task>` without `--json`) in an untrusted directory with its input closed left the question pending and the process exited 0 with no result, and an empty line or `1` arriving on the pipe counted as "Trust this workspace". Now such a start says on stderr that there is no terminal to confirm trust, counts the workspace as not trusted, writes nothing to the trust list and exits 1 (the one-shot "not started" code); `--trust-workspace` remains the explicit scripted form. A one-shot task whose user chooses Exit at the prompt also exits 1 instead of 0. Underneath, `askQuestion()` now rejects with `InputEndedError` when the input ends before an answer (Ctrl-D, a closed pipe) instead of staying pending, so no prompt can end the process silently; the checkpoint-restore and Agent-integration `[y/N]` prompts treat an ended input as no. Tests: unit tests for the prompt helper and a real-CLI test that pipes nothing, an empty line and `1` into an untrusted one-shot and interactive start.
- CLI: `xiu --help` now ends with the commands that run without an interactive session (`xiu doctor [json]`, `xiu report …`, `xiu report runs`, `xiu recover [status]`, `xiu recover abandon <run id>`, `xiu audit …`, each with a one-line purpose), the exit codes of a one-shot task (0 / 2 / 3 / 1, taken from the same constants the runtime uses) and the note that slash commands run only at the interactive prompt, plus links to the guides. Before, the help listed only the options, so a script author had no way to discover `xiu report` or the exit codes from the terminal. A test runs the real `--help` and checks the text, and that the commands guide's launch-parameter table names the same commands.
- CLI: a one-shot run whose task is a slash command (`xiu /help`, `xiu /doctor json`, `xiu "/skils"`) no longer sends that line to the model as a task. It stops before trust, plugins or the model with exit code 1 and explains on stderr: a listed command names the script form where one exists (`In a script, use xiu doctor [json].`; also `xiu report`, `xiu recover`, `xiu audit`, `--check-update` / `--update-doctor`, `--resume`, `--list-sessions`, `--language`, `--model`, `--provider`), an unknown word gets the closest commands; with `--json` the `result` line carries `outcome: "not_started"` and that message. Paths and task text are untouched as at the prompt. `/help <command>` (`/help mcp`, `/help /mcp`, `/help plan on`, `/help quit`) lists only that command's usages, and the "has no usage" message now points at `/help <command>` instead of the whole list.
- CLI: a known command followed by something its handler does not recognise (`/mcp premissions`, `/plan onn`, `/history bogus`, `/quit now`) is answered at the prompt too: `/mcp has no usage "/mcp premissions". Did you mean /mcp permissions? Available: /mcp, /mcp permissions, … (see /help).` Before, such a line fell through to the model as a task. While a task runs, the `steer>` prompt now names what it accepts (`/cancel`, `/exit`, `/queue`, `/clear-queue`, `/status`, `/diff`, `/check`, `/diagnostics`, `/details`, `/paste`, `/credentials`, `/web`, `/language`, exported as `RUNNING_TASK_COMMAND_WORDS`) and answers any other listed command (`/mcp`, `/plan on`) with "not available while a task runs" instead of sending it to the model as steering. `/queue <task>` typed while no task runs says `/queue is available while a task is running` instead of becoming a task; `/skills install` without an argument prints its usage instead of reaching the model; `/plan on` and `/plan off` appear in `/help`. Tests cover the three cases in both languages and check that the steer> word list covers every word its handler dispatches on.
- CLI: a lone slash word the interactive prompt does not recognise (`/skils`, `/hepl`, `/Cancel`) is no longer sent to the model as a task. The prompt prints `Unknown command /skils. Did you mean /skills? Type /help for the full list.` and that the line did not reach the model; the same happens at the `steer>` prompt while a task runs, where the typo used to become a steering message. A slash that starts a path (`/etc/hosts explain`, `/tmp what is here` when the path exists), a word with a dot or a second slash, and every listed command or alias (`/quit`, `/model`) behave as before; one-shot runs are unchanged. The `/help` list moved to `src/slash-commands.ts` so tests can read it: one test checks that every slash word the loop dispatches on is listed there and that every listed command is mentioned in the Chinese guides. Test: the provider-recovery dead-lock test pins the process start-time probe, so the Windows runner's `Get-Process` answering "unknown" for an exited child's PID no longer fails it intermittently.
- CLI: the failures of the plugin, Skill, MCP, credential, report, Diff, check and queue commands, and an error thrown by a task in the interactive loop, are explained with the same "cause / next step / diagnostic / detail" lines whenever the error catalog recognises the cause (a damaged `~/.xiu/extension-permissions.json` during `/mcp permissions` or `/plugin approve`, a network, TLS or HTTP failure during `/mcp login`, `/mcp test` or `/skills install`); any other failure keeps its single `operation: message` line, now with secrets redacted, instead of gaining a generic "retry" step. New `describeFailure()` in `user-facing-errors.ts` makes that choice; the startup failure handler uses it too. Before, these commands printed the raw message only, so the `config/extension-permissions` explanation added in the previous entry had no command that showed it.
- CLI: a startup that stops on a damaged configuration file now explains itself the way provider and network failures already do: `Xiu could not start: <cause>`, `Next step: <what to do>`, `Diagnose: xiu doctor`, `Detail: <code> · <the owner's message, path included>`, in the language the command line, `XIU_LANGUAGE` or the settings file selects. Four new codes in the error table: `config/settings`, `config/trust-store`, `config/extension-permissions` and `config/mcp`. The loaders throw the new `ConfigFileError` (kind, file, the unchanged message, the system error code when there was one) and keep failing closed; a `--json` run still ends with the `result` line carrying the raw message and exit code 1, with the explanation on stderr. An MCP config that does not load (`~/.xiu/mcp.json` or the workspace's `.xiu/mcp.json`) is explained the same way in a one-shot run and under `/mcp`, with the server entry to fix in the detail, and the run goes on without MCP as before. A provider configuration failure at startup is explained once instead of the explanation followed by a raw `Error:` line. Any other startup failure keeps its raw `Error: <message>` line. Real-CLI tests cover the trust list, the settings file (in Chinese) and a workspace MCP config.
- CLI: `xiu doctor` now lists Xiu's other configuration files next to the settings file: the trust store (`~/.xiu/trusted-workspaces.json`), the extension permission grants (`~/.xiu/extension-permissions.json`), the user MCP config (`~/.xiu/mcp.json`) and, for a trusted workspace only, the workspace's `.xiu/mcp.json`. Each shows read (with a count), absent, or a failure with the cause and the consequence: a damaged trust store makes every workspace untrusted, damaged grants make every Skill and plugin unapproved, a damaged MCP config connects no server. The workspace-records section also says when the trust store itself could not be read instead of calling the workspace untrusted. New read-only `inspectTrustStore()`, `PermissionGrantStore.inspect()` and `inspectMcpConfig()`; the owners keep failing closed, and the permission store's error now names its file. Before, these files failed silently at the point of use (plugins just showed `inactive`, MCP just did not connect) and the doctor said nothing about them.
- CLI: a damaged `~/.xiu/settings.json` (a JSON syntax error, a directory in its place, no permission) no longer stops `xiu doctor`. `SettingsStore.inspect()` reads the file without throwing and reports `read`, `absent` or `unreadable` with the cause; the doctor runs with the defaults and its installation section shows the file's state, a damaged file as a failure with the fix (repair the JSON or move the file away). Every other command still fails closed, now with the file path and that hint in the message (`Could not read Xiu settings file <path>: <cause>. Fix its JSON or move the file away…`); before, the message had no path and `xiu doctor` died with it, so the one command meant to diagnose the installation could not say what was wrong.
- CLI: a skill the registry finds but does not list no longer disappears silently. `SkillRegistry.refresh()` records each one with a reason (`unreadable` with the system error code, `shadowed` by a same-named skill of a higher-precedence scope, `oversized` plugin skill, `truncated` when a root holds more than 300 `SKILL.md` files) and `issues()` returns them; `/skills` prints one line naming them (folder names only, never a path) before the list. Before, an unreadable `SKILL.md` was skipped without a word and a global skill hidden by a project skill of the same name looked uninstalled.
- CLI: `xiu doctor json` prints the diagnostics report as one JSON document (`version`, `generatedAt`, `status`, `sections[]` with each item's `id`, `level` and both languages' label, summary and detail), the same already-redacted report the text form shows, so scripts and CI can gate on `status` or a single item without parsing text; exit codes are unchanged (1 on a failure, also in JSON mode). `xiu doctor` followed by any other word is now a usage error (exit 1, usage line on stderr); before, `xiu doctor <typo>` was sent to the model as a one-shot task. `--json` still cannot be combined with `doctor`. The argument handling lives in `src/commands/doctor-command.ts` with its own tests.
- CLI: `xiu doctor` gains a "Workspace records" section between Windows and System. It reads the current workspace's task-run journal and session logs the way `/report runs` and `/resume` do and reports how many are readable, how many are not and why (`corrupt ×1`, `EISDIR ×1`, never a path), then performs the same strict interrupted-task check a one-shot run performs: a pending interrupted task is a warning that names the run and points at `xiu recover status` / `xiu recover abandon`, and a check that cannot complete because of a corrupt record is a failure that says new one-shot runs will return `not_started` until the file is removed. An untrusted workspace is not read at all; the section says so as information, not a warning. The probe is read-only and never writes a record or lock.
- CLI/Desktop: one unreadable session log (a directory in its place, no permission, an I/O error) no longer hides every other session. `listSessions` skips it and the new `listSessionsWithIssues` names it with the system error code, never a path; `/resume`, `/history sessions` and `xiu --session-list` print one line saying how many logs were skipped and why, the desktop task list keeps the readable sessions, and loading the broken session by id fails with that code instead of "session not found". Before, `/resume`, `/history sessions`, `--resume`, the desktop's workspace snapshot and every execution report in the workspace failed or degraded on the first bad file (the report called every run's log "unreadable").
- CLI: one unreadable task-run record (corrupt JSON, another schema version after a downgrade, another workspace's file, an unsafe entry) no longer takes down every run list. `TaskRunJournal.recent()` skips what it cannot read and the new `scan()` names the skipped records; `/report runs`, `xiu report runs` and `/diff runs` end with one line saying how many records were skipped and why (`corrupt ×2`), never a file name or path. Before, the whole list, `run:` selection and the desktop's recent-task views failed on the first bad file. The interrupted-run check is unchanged and still fails closed on an unreadable record, so a corrupt file cannot hide an interrupted task from a new one-shot run.
- CLI: `/diff runs` and `/diff run:<selector>` tell a saved change record that cannot be read (corrupt, altered or over its limits) apart from a run that has none. The list shows `!` instead of `-` for such a record, and the replay refuses with a localized message naming the reason (the loader's own check or the system error code, never a path) and pointing at `/diff workspace`. Before, the list showed `-` as if no record existed and the replay surfaced the loader's raw English message.
- CLI/Desktop: the execution report (`/report`, `xiu report`, the desktop's "报告与诊断") now says when the run's session log is missing, unreadable or has no turn for the run. Those three cases used to be swallowed and the report showed "none recorded" under file changes, which reads as "the task changed nothing". The report gains a `sessionLog` field (`read`, `missing`, `unreadable` with the error code and never a path, `turn-missing`); Markdown and HTML add a "Sources" line naming the cause and show "unavailable (see Sources)" for file changes and key actions, while the run record's own phases, verification, failures and the audit counts are still reported. Tests cover all four states through `xiu report` in both languages and all three formats.
- CLI: `xiu audit [approvals|credentials] [json] [limit]` lists the workspace's local security-audit records without entering the interactive loop, the scriptable `/audit`: newest last, 50 by default and up to 500, `json` for one JSON document with the records and the ledger's truncation and invalid-line counts. Only the ledger's fixed fields are shown (time, category, action, outcome, risk, decision source, scope, redacted subject), records of other workspaces never appear, trusted workspaces only, exit 0 when listed (also when empty) and 1 on a usage error, an untrusted workspace or an unreadable ledger; not combinable with `--json`. Test harness: the piped approval-boundaries test no longer races the CLI's stderr explanation ("Task stopped: …") against the stdout prompt; after the prompt it waits for the output to settle before asserting, which was an intermittent failure in local full runs.
- Desktop security: the shared workspace host now records every tool approval it decides (a prompted decision, an automatic approval in "帮我批准" or Full Access, the always-confirmed worktree integration) in the same local security-audit ledger the CLI writes, `~/.xiu/security-audit.jsonl`, with the CLI's fixed fields: outcome, risk, decision source and scope, never the description, preview or tool arguments. `/audit approvals` and the execution report's security count therefore cover desktop runs; before, only CLI approvals were recorded. The ledger stays local and an unwritable file never changes a decision. Tests drive a real host through automatic and prompted approvals and check the records and that no tool argument reaches the file.
- Desktop: the "报告与诊断" panel now builds its execution report through the same query as the CLI's `/report` and `xiu report` (`src/execution-report-query.ts`: the run, the session turns of its task chain and the workspace's audit facts), so a run reads the same on both surfaces. Before, the desktop built the report from the run record alone and showed no file changes for a task that had changed files. A test renders the same run through both paths and compares the text.
- CLI: a plain one-shot run (`xiu <task>` without `--json`) now exits with the same codes as `--json`: 0 completed, 2 unverified, 3 the model asked a question, 1 failed, cancelled or paused. Before, only `unverified` set a code, so a failed task or an unanswered question exited 0 and a script could not tell. End-to-end tests drive the real CLI with a fake model through all three non-zero outcomes in both modes.
- CLI: `xiu recover [status]` and `xiu recover abandon <run id or prefix ≥ 4>` handle an interrupted task without the interactive menu, for scripts and CI. `status` prints the task, its last recovery point and the side effects awaiting verification, and exits 2 when an interrupted run exists (0 when none); `abandon` marks the run abandoned without replaying anything, only when the given id matches it, and a wrong id changes nothing. Resuming is not offered non-interactively. Trusted workspaces only; not combinable with `--json`. The one-shot `not_started` message now names this command. An end-to-end test also covers a one-shot run paused by its task budget: later runs are refused until `xiu recover abandon` clears the paused record, then they run.
- CLI: `run:<selector>` on `/diff`, `/report` and `xiu report` no longer misreads a run-id prefix that happens to be all digits (about one UUID in forty starts with eight digits, such as `69049616`) as a list index: a digits-only selector that identifies exactly one run by prefix selects that run, otherwise it is the 1-based index as before. This was the intermittent failure of the task-history end-to-end test on CI.
- CLI: a one-shot run (`xiu <task>`, `xiu --json <task>`) that finds an interrupted task in the workspace, or cannot read the task-run journal, now exits 1 and, with `--json`, writes the `result` line with `outcome: "not_started"` and the reason. Before, it printed the explanation and exited 0 with no `result` line, so a script could read "nothing happened" as success. A piped interactive start (no terminal to answer the resume/abandon menu) also exits 1 and leaves the record untouched; choosing "Exit" in a terminal still exits 0. Four end-to-end tests drive the real CLI with a crashed run's record.
- CI: when a test fails, the CI test runner's workflow annotation now carries the whole TAP diagnostic block (assertion message, expected and actual text), not only the key names, so an intermittent failure can be diagnosed from the annotation after the job log is gone. The background-task tests poll by wall clock with a shared 90-second budget instead of a fixed number of attempts, because shared macOS runners can take longer than 30 seconds to start a detached worker while other test files run.
- CLI security: option menus now fail closed when there is no interactive terminal (piped stdin/stdout, CI). Before, a menu silently took its first entry, so a scripted session could approve a plugin manifest, trust a publisher, delete or forget credentials, allow an MCP OAuth login or resume an interrupted task without anyone choosing. Now the menu counts as cancelled, prints one line saying why, and the caller's own cancellation message follows; only harmless pickers that are followed by a typed prompt (`/provider add` template, `/provider remove` before its [y/N]) still take the first entry. An end-to-end test drives `/plugin approve` over a pipe and checks nothing is approved.
- CLI: approval boundaries now have a fixed end-to-end test through the real CLI over a pipe with a fake model: `--yes` auto-approves execute-risk commands but a dangerous one (`rm -rf …`) is denied and never runs, a piped session without `--yes` denies writes instead of guessing, Plan mode stays read-only even with `--yes`, and a `--json --yes` one-shot run records the denied approval and exits 1. Two things the test surfaced are fixed: a denied approval in a piped session no longer discards the live task view (the tool's start line and the denial stay in the output), and the runtime's approval effects, recovery notes and failure reasons follow the CLI language instead of always being Chinese (the desktop keeps its Chinese default).
- CLI: a one-shot run (`xiu <task>`, `xiu --json <task>`) now prints a one-line notice on stderr when it cannot save the turn to the session history, so the user knows `/resume` will not show that turn; the task result is unaffected. Before, the failure was swallowed silently. Desktop CI: the Full Access dialog smoke test retries the screenshot a bounded number of times, because the virtual display's compositor occasionally fails the first capture.
- CLI: in a piped (non-TTY) interactive session the prompt comes back as soon as a task finishes, and the task's output streams while it runs. Before, the piped input path ignored the task's completion signal, so the result and the next `xiu> ` prompt only appeared after another input line arrived, which stalled scripted sessions. A new end-to-end test drives the real CLI over stdin with a fake model that writes a file and checks `/diff runs`, `/diff run:<selector> [file]`, `/report runs`, the saved change record and `xiu report run:<selector>`.
- CLI: `/mcp read` can read MCP Resource Templates. The interactive picker lists templates next to resources, `/mcp read <server> <template name> name=value …` pre-fills variables and missing ones are prompted for; the template is expanded per RFC 6570 (`{var}`, `{+var}`, `{#var}`, `{.var}`, `{/var}`, `{;var}`, `{?var}`, `{&var}`; `*` and `:n` modifiers are refused) with every variable supplied by the user, the resulting URI is printed before the request, and the content is still shown as untrusted remote text. Plain URIs behave as before.
- CLI: when a task finishes, the CLI saves the final bounded, redacted change report to the workspace's `.xiu/task-change-history/<runId>.json`, the same record the desktop writes (so each side's "recent tasks" can show the other's changes). `/diff runs` lists the 50 most recent runs with the number of changed files each record holds, `/diff run:<number|run-id prefix>` replays a run's saved report in the `/diff task` layout, and `/diff run:<selector> <file>` prints that file's saved complete diff. A run without a record says so instead of showing the current workspace diff.
- CLI: `/report runs` and `xiu report runs` list the 50 most recent task runs of the workspace; `run:<number>` or `run:<run-id prefix>` on `/report`, `/report export …` and `xiu report` reports that run instead of the latest one.
- CLI: `--trust-workspace` treats the workspace as trusted for this process only, replacing the interactive trust prompt for scripts and CI on a checkout the user controls. Nothing is written to `~/.xiu/trusted-workspaces.json`, only the command line can set it, and approvals, `--yes` scope and Plan read-only are unchanged. The getting-started guide gains a read-only GitHub Actions review example.
- CLI: `xiu report [markdown|json|html] [summary|details] [path]` exports the latest task's execution report without entering the interactive loop: same data and formats as `/report export`, stdout when no path is given, human-readable notices on stderr, existing files overwritten only with `--yes`, trusted workspaces only, exit code 0/1. The report collection is shared with `/report`.
- Desktop: tasks now reuse plugins approved in the CLI (`/plugin approve`): provider, MCP tool and Skill contributions of approved plugins are loaded into the trusted workspace host through the same registries the CLI uses. The desktop adds no approval entry of its own; unapproved plugins stay inactive and plugin MCP servers still require their permission manifest to be confirmed in Extensions.
- Desktop security: every renderer → main IPC invoke channel now validates its arguments at runtime against a per-channel schema (`apps/desktop/main/ipc-schema.ts`: types, discriminants, bounded lengths and counts; undeclared fields are dropped, surplus arguments rejected) after the trusted-sender check and before the handler runs; a channel without a schema cannot be registered. Domain rules stay in the controllers, and rejection messages name the channel and field without echoing values.
- CLI: `xiu --json <task>` runs a one-shot task as a machine-readable JSON Lines stream. stdout carries a `session.started` line, every redacted runtime event (the same `schemaVersion: 1` protocol the desktop uses) and one final `result` line whose `exitCode` matches the process exit code (0 completed, 2 unverified, 3 waiting for an answer, 1 failed or not started); human-readable progress moves to stderr. The flag never reads decisions from a pipe: untrusted workspaces return `not_started`, `--yes` keeps its limits and dangerous actions stay denied.
- CLI: `/report export html <path> <summary|details>` writes the execution report as one self-contained HTML file (inline styles, no scripts, no external resources, a CSP that forbids both, light/dark aware, every value escaped).
