# Xiu 产品发展计划书：从功能齐备走向日常好用

> 版本：计划书 1.0｜日期：2026-09-16｜后续状态：P0＋P1 已获批准并完成候选实现；P2–P4 尚未进入实施。
>
> 本稿保留最初评估时的依据与建议，不替代当前有效的 ROADMAP、SECURITY 或版本设计。最初评估轮次仅新增本计划书；后续获批范围、实现与交付状态以正式路线图和当前版本设计为准。

## 1. 决策摘要

我的建议是继续做 Xiu，保留 TypeScript 实现与已有资产，把未来两个版本的主要投入放在“完成真实编码任务的质量”和“人与 Agent 协作的顺畅程度”。

Xiu 已经具备终端输入、会话恢复、工具调用、代码索引、多模型、MCP、插件、多 Agent、检查点和报告等基础。当前需要的不是再列一张更长的功能表，而是让这些能力在同一个任务中稳定协同：理解需求、找到代码、正确修改、执行检查、解释结果，遇到错误能纠正，用户随时能插话、取消和接着做。

上一版只列 `/check`、`/doctor` 和重构的计划过于局部。这些入口可以改善体验，但支撑不了“媲美 Claude Code、Codex、Pi”的产品目标。本稿将执行核心、模型适配、上下文、交互与交付工作流列为主线。

建议定位：**中文体验自然、Windows 原生路径顺畅、支持自选模型，能把真实项目任务做完并让改动可审查的终端编码助手。**

“中文 + Windows + 自选模型”是切入点，不是永远限制支持范围。“可信执行”是底层要求和长期资产，不宜让用户为了使用这些能力先学习审计体系。

未来 8–12 周的目标是做出一个值得每天使用的候选产品，而不是承诺追平三家产品的全部能力、模型智能、生态和市场。更完整的集成与跨平台成熟度放入后续 3–6 个月的滚动方向。

推荐决策：

1. 保留现有技术栈和可复用模块，采用增量改造。
2. 先打磨单 Agent 编码闭环，再扩大并行任务和生态。
3. 优先支持 Windows 下的 TypeScript/JavaScript 日常开发；通用文件与命令能力继续服务其他语言。
4. 模型质量和执行框架质量分开衡量，不能把单一免费模型等同于产品上限。
5. 评测服务开发；取消旧版“完成大批真实对照后才能优化”的前置要求。
6. 自动检查由开发流程承担，用户只集中体验每个候选版本。

## 2. 评估依据与结论边界

本次依据本地分支 `codex/v0.18.0-evaluation-design`、提交 `e0aaf7c`，阅读当前路线图、安全规则、设计稿、README、快速开始及关键代码和测试；并行检查执行核心、交互流程与工程结构。参考了最初的《XIU_评估报告》《WORKPLAN》和仓库内 2026-08-25 评估报告，但只将与当前代码相符的结论用于排序。

本地代码统计：`src` 有 66 个文件、约 22,068 行（含空行）；`test` 中有 61 个 `.test.ts` 文件。`cli.ts` 约 3,646 行，`agent.ts` 约 1,409 行。行数说明职责集中，不直接证明质量差。

当前包声明为 0.18.0，路线图记录公开版为 0.17.0。本轮没有查询 npm 最新发布状态，未来发布前必须重新核对 Registry。

本轮是产品与架构评估，不是完整安全审计、真实终端体验测试或竞品性能基准；没有重跑完整测试，不能将历史通过数写成今天的实测结果。以下区分三类内容：代码已确认的事实、需要测试复现的风险、建议目标。

| 观察 | 依据 | 结论 |
| --- | --- | --- |
| 交互、恢复、报告和扩展已经存在 | `src/cli.ts`、`session.ts`、`interactive-ui.ts`、`execution-report.ts`、`mcp.ts`、`plugins.ts` | 应整合打磨，不能重复计为全新功能 |
| 中文模式未启用模型增量输出 | `src/agent.ts:491` | 中文等待感有明确实现原因，改善优先级高 |
| 交互模式缓冲增量文本 | `src/cli.ts:933–943` | 需要重新区分流式草稿、进度事实和最终完成状态 |
| 验证识别依赖命令文本与字符串结果 | `src/tools.ts:239–256`、`:759` | 应建立结构化检查证据，避免无意义命令被当成验证 |
| 循环保护主要比较工具名和参数 | `src/loop-guard.ts` | 换路径但不断失败的情况需要结果感知的停滞识别 |

还有一个必须纠正的判断：上次真实评测留下 14/30 条 trial，1 条通过、13 条预算失败，文件状态仍是 `running`。评测器只给模型四个 `eval_*` 工具，没有列目录/搜索工具，而示例任务没有告诉模型实际文件名。`eval_verify` 是受限 fixture 检查，也不等于产品运行真实测试命令。因此，该结果只证明那套受限配置出现了失败，不能证明 Xiu 产品成功率为 1/14，也不能把责任直接归于 Agnes 模型。

旧报告中“唯一”“竞品做不到”“构造函数迁移零风险”“固定成本能下降 40–60%”等表述，本方案均不采用。应以当前事实和实际对照建立结论。

## 3. 如何理解“媲美”

首先把目标落在可比较的用户任务上：修一个 bug、增加一个小功能、完成一次跨文件重构、解释陌生模块、审查一组改动、接着处理昨天的任务。暂不以功能数量、模型调用数量或长时间无人值守作为成功标准。

官方资料体现出值得借鉴的不同侧重：

| 产品 | 本次核对到的能力 | 对 Xiu 的启示 |
| --- | --- | --- |
| Claude Code | 查看代码、执行工具、根据反馈调整的任务循环；技能和扩展连接开发工作流 | 让“找代码→修改→检查→继续”顺畅，优先改善日常动作。[官方工作原理](https://code.claude.com/docs/en/how-claude-code-works) |
| Codex CLI | 终端内探索、编辑、运行、审查、会话继续以及脚本化入口 | 完成任务与审查结果应使用一致的执行状态和证据。[官方 CLI 文档](https://learn.chatgpt.com/docs/codex/cli) |
| Pi | 精简核心、可扩展机制、交互/JSON/RPC/SDK 入口 | 减少内核承担的产品分支，给高级工作流稳定的扩展点。[官方仓库 README](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/README.md) |

这些是基于文档的产品设计参考，不构成实测排名。这里的 Pi 指原 `badlogic/pi-mono` 指向的编码 Agent 项目。

另外，Codex 官方明确区分操作系统层的沙箱和审批政策；Xiu 当前 README 明确说明自己不是容器沙箱。减少询问不能仅靠放宽命令分类来实现，应先把许可范围和真实执行边界做清楚。[官方沙箱说明](https://learn.chatgpt.com/docs/sandboxing)

检查点也不等于所有副作用可撤销。Claude Code 官方同样说明 Bash 修改不在普通文件编辑检查点的恢复范围内；Xiu 应准确说明自己的覆盖面，不能承诺万能撤销。[官方检查点说明](https://code.claude.com/docs/en/checkpointing)

建议将“媲美”拆为三层：

- **近期必须达到：**日常任务入口简单、执行有反馈、失败能纠正、改动能看清、结果不误报。
- **中期争取达到：**长任务不丢目标、跨文件理解稳定、模型切换可靠、恢复和审查顺手。
- **长期按需求选择：**IDE 集成、团队并行、浏览器验证、远程执行、生态规模。它们不应一次性全部进入核心。

## 4. 目标用户与产品范围

第一批目标用户是使用 Windows/PowerShell、维护 TypeScript/JavaScript 项目、愿意使用终端并有可用模型的个人开发者及小团队。其次是希望使用自有 API、本地模型或组织批准端点的开发者。

首轮目标是让 5–10 名试用者用自己的真实任务持续使用，而不是立即进入企业治理、计费平台和复杂私有化销售。这个人数是招募目标，本轮没有证据说明项目已有这些用户。

主要价值承诺：

1. **能把任务做完：**理解现有代码，做有边界的修改，并检查结果。
2. **使用时省心：**能看到当前行为，插话有效，取消及时，错误容易理解。
3. **改动可掌握：**看清本任务改了什么、哪些检查通过、哪些还有风险。
4. **选择不过载：**常见模型和项目有合理默认值，高级配置按需出现。

中文优先不意味着强制改写代码、文件名和工具输出。Windows 优先不意味着宣称其他平台不可用；各平台成熟度仍按事实标注。

## 5. 五个优先打通的用户流程

### 5.1 安装后完成第一个任务

流程：安装 → 本地环境检查 → 配置或选择模型 → 信任项目 → 输入任务 → 得到第一份可检查的结果。

已有的 setup 模式、Provider 管理和能力探测继续使用。新增的工作是缩短默认路径、解释缺失条件、给出下一步动作；不让用户先理解 failover、routing、插件签名和凭证迁移。

完成标准：有可用凭证和正常网络时，陌生用户无需维护者旁边解释即可完成一个小任务。将“10 分钟内完成首个任务”作为试用目标，记录依赖下载和模型等待，不能把外部耗时伪装成客户端性能。

### 5.2 修复一个真实 bug

流程：读取报错 → 定位入口与调用方 → 复现或建立最小失败检查 → 修改 → 相关测试 → 展示任务改动和未验证部分。

优先改善路径查找、patch 冲突、Shell 参数、错误反馈和循环纠错。若测试环境不可用，明确标记完成范围，不捏造“通过”。

### 5.3 增加一个跨文件小功能

流程：明确边界 → 找相关符号和约束 → 更新接口与调用方 → 补检查 → 复查兼容性 → 汇总。

简单任务直接做；涉及接口取舍时只问影响结果的问题。计划随进展更新，不要求用户逐步批准文件编辑。

### 5.4 用户中途纠正方向，随后继续

流程：任务运行 → 用户补充或改变要求 → 显示已接收/待处理状态 → 在安全边界采用新要求 → 保留未取消的原目标。

补充要求、取消某项要求和明确替换目标必须可区分。当前 prompt 把所有 steering 都规定为追加，有可能过于僵硬；改进应允许用户明确改方向，同时保持安全与未完成工作状态。

### 5.5 审查改动并交付

流程：查看本任务与原有改动 → 查看测试证据 → 请求只读审查 → 修复确认问题 → 用户选择是否暂存/提交/推送。

任务级 diff、检查结果和 review 入口应放在一起。提交、推送、合并及发布按用户明确请求执行；完成任务不自动意味着执行这些动作。

## 6. 核心能力建设方案

### 6.1 执行核心：让错误变成下一步信息

优先引入内部结构化工具结果，保留旧工具的兼容适配器，不一次改完所有工具。

建议表达：状态、简短输出、错误类别、是否重试、是否存在未知副作用、文件变化引用、检查证据。终端展示、Agent 决策、诊断和完成判定都消费同一份事实，避免各处重复正则解析文本。

改进点：

- 路径不存在：提供可行的目录/搜索入口；不能靠猜文件名循环。
- 替换失败：报告匹配数或文件已变化，要求重新读取再生成 patch。
- 参数错误：只修输入；权限拒绝不冒充临时故障重试。
- 同类失败：按原因和目标聚合；普通失败命令不能被当作有效进展重置循环计数。
- 成功进展：由读到新证据、修改生效、测试状态变化等事实支持，不按调用次数认定。
- 未知副作用：保留并查询，禁止自动重放。
- 并行：先仅并行彼此独立的只读操作；编辑、依赖安装和检查按依赖安排。

不做目标：用更多自动反思轮次掩盖工具契约缺陷，或靠无限增大预算追求完成。

### 6.2 模型层：优先兼容正确，再追求自动选择

保留 Agnes/OpenAI/Anthropic/兼容端点等现有支持，先改善协议适配和使用体验。

- 统一文本、工具调用、结果、结束原因、Token 用量及取消事件。
- 原始 Provider 响应不得作为跨 Provider 通用历史；敏感或隐藏推理字段不得进入普通日志。
- 对需要协议专属状态的模型，使用显式能力契约；不为了切换方便保存被安全规则禁止的内容。
- 同协议换模型和跨协议换 Provider 分别测试；能力不满足时给出明确原因。
- 流式断线、工具参数不完整、响应截断和速率限制分别处理。
- 将 Provider 的结束原因纳入统一响应；达到输出上限不能与正常完成混为一谈。输出上限按已验证的模型能力设置，不在所有模型上固定一个数值。
- 缓存统计只采用 Provider 实际返回的数据；缺失为未知，不记为零成本或已命中。
- 准备“常用”“复杂任务”“低成本”配置预设；先由用户明确选择，后续再验证分阶段路由是否有收益。
- 新增原生 API 适配器只针对实际需要且现有通道不支持的能力，不为数量增加接入。

能力上限需要合适模型支持。Agnes Enterprise Flash 可继续作为用户已有配置，但“免费”是用户提供的计费前提，不是质量结论，也不是所有任务只使用这一模型的理由。

本方案不指定未经验证的最新模型，不更换用户默认 Provider，不启动新的收费比较。后续做模型选择时再核对当时能力、条款和价格。

### 6.3 上下文与检索：给模型恰当的信息

现有 ProjectIndex、AST 关系、任务契约和压缩继续使用。

- 构建稳定的上下文层次：核心规则 → 已批准的项目指令 → 当前目标 → 相关代码 → 最近工具证据。
- 项目指令增加来源和作用范围展示，明确根目录与子目录指令如何生效；沿用工作区信任门禁。
- 工具和提示词按启用能力组织，未配置媒体或扩展时不加入无关细节；保留动态发现与回退路径。
- 搜索优先结合路径、符号、引用和当前任务；读取带行号、边界与可继续读取的提示。
- 文件变化后使相关缓存和验证失效；外部编辑同样考虑。
- 请求预算应包含 system prompt、工具 schema、历史消息和输出预留。当前会话估算不足以代表完整请求长度，应先修这一点再优化压缩阈值。
- 搜索或索引达到文件数上限时明确显示覆盖范围和继续查找方式；未搜索完整仓库不能把局部“无匹配”说成全仓不存在。
- 压缩保留当前目标、用户最新决策、已完成证据、失败尝试与下一步；长期记忆只记录稳定偏好和已确认项目事实。
- 记忆默认本地、可查看、可编辑、可关闭；不自动存凭证，也不让记忆授予权限。
- 长工具输出保存有界、可定位的证据，不能只留下头部截断后要求模型猜测。

近期不引入向量数据库和复杂 RAG 服务。先证明现有本地索引在目标项目上的不足，再选补充技术。

### 6.4 交互：有响应、可打断、不抢输入

- 中文与英文都具备及时反馈。先做安全的分段输出/可更新草稿展示，再决定繁简转换的最佳边界。
- 内容尚未经过完成判定时不显示“任务已完成”；最终状态由执行事实单独展示。
- 中文转换、Markdown 和秘密脱敏要适应跨 chunk 情况，不能为了流式显示破坏原有保护。
- 工具输出渐进展示，默认摘要、按需展开；避免刷屏和持续“思考中”。
- 插话、排队、取消、后台运行使用可解释的状态；取消请求与进程真正退出分开显示。
- 保留原有输入、历史、图片引用和 `/queue` 能力，重点修粘贴、宽字符、窗口缩放、滚动和恢复一致性。
- 权限请求写清对象、动作、影响和有效范围；许可变化时失效，不用模糊的“以后全部允许”。
- 首屏先展示任务相关信息，诊断细节按需展开。
- 命令面板使用统一注册表，按常用/项目/扩展/高级配置分组，支持中英文描述搜索；运行中不可用的指令清楚标注，避免被误送为普通补充要求。
- 会话增加搜索、可修改标题和继续摘要；用轻量元数据索引避免选择器每次读取所有完整 JSONL。会话分支留待实际需求，跨设备同步暂缓。
- 待用户回答的问题连同原目标一起恢复，避免恢复后的一句“是”被当成新任务。

不为视觉效果立即重写全屏 TUI。先用终端回放与短时人工体验确认卡点。

### 6.5 任务级变更、检查与审查

建立任务开始时的工作区状态记录，覆盖 tracked、staged、untracked 及必要的内容摘要；用于区分已有变更与任务期间变化。遇到外部编辑或重叠修改时标记来源不确定，不能假装精确归因。

首期不自动 stash、reset 或恢复整个工作区。现有文件检查点继续承担明确范围的恢复；Shell、网络和其他外部副作用保持独立说明。

拟提供的入口（名称以实现设计为准）：

| 入口 | 行为 | 性质 |
| --- | --- | --- |
| `/diff` | 选择本任务、整个工作区、暂存区；展示新增/删除/修改 | 改善已有功能 |
| `/check` | 发现标准项目检查、选择执行、查看结果 | 复用 project_info/validate_project 的新用户入口 |
| `/review` | 对指定改动做只读审查，给出文件定位、依据和优先级 | 新工作流；会调用模型时必须计入现有任务预算 |
| `/report` | 展示变更、检查、问题与未完成事项 | 整合已有记录 |

`/check` 首期只支持 npm 标准脚本，然后加入包管理器与子项目选择。脚本存在不意味着安全或有效，仍按执行审批处理；Plan 模式只发现不执行。

验证证据关联执行时的输入与文件状态。之后又修改代码，相关“通过”自动过期。自定义脚本退出码零只证明该进程按约定退出，不自动证明所有用户需求正确。

当前 Agent 已有“发生修改后清除已验证状态”的基础。本项是在此之上补齐证据绑定、必要检查集合和外部变化处理，而非从零新增验证失效机制；同一批操作中有一项成功，也不能覆盖另一个必要检查的失败。

Review 结论与测试结果分开；不把另一个模型说“通过”当成可执行证据。允许用户明确请求“只检查，不改代码”。

### 6.6 扩展与自动化：让能力可组合

MCP、Skills、插件与多 Agent 已存在，优先改善稳定接口、发现、错误和权限说明。

中期可以提供稳定 JSON 事件输出和一个小型程序化入口，让 CI、编辑器或自定义前端消费同一套 runtime。先稳定协议与取消语义，再做 IDE 面板，不从独立桌面应用开始。

多 Agent 先做限定角色的并行调查或独立审查，再做明确文件边界的 worktree 实施。每个任务展示成本、运行状态和结果来源，仍需程序化验证与显式集成。默认不开一群 Agent 处理简单任务。

浏览器验证先作为可选 MCP/扩展处理前端页面测试，明确登录状态、网络与写操作授权；不并入当前原生只读联网工具，也不重造完整浏览器平台。

## 7. 架构方案与技术取舍

推荐继续 TypeScript/Node。现有模块约两万多行，有可复用资产，当前没有证据证明换语言或整体迁移到其他 Agent 框架更快。

目标依赖方向：

```text
终端 UI / 一次性 CLI / 后续 JSON 接口
                 ↓
      应用服务：任务、会话、检查、审查
                 ↓
      Agent runtime：计划、模型、工具、完成判定
          ↓             ↓              ↓
      Provider 适配   工具执行与审批   上下文与任务状态
          ↓             ↓              ↓
      统一消息协议   结构化执行结果   证据、检查点、会话
```

实施原则：

1. UI 只消费事件，不自己重新推断工具是否失败或验证是否通过。
2. 核心不直接打印终端；结构化事件包含版本、任务/操作标识、阶段和有界数据。
3. 模型完成文本和系统完成状态分离。
4. 审批与执行集中在一条可测试路径；CLI 快捷入口也不能跳过。
5. 兼容适配器逐个迁移现有工具；保留旧 session 读取，迁移失败时明确报错。
6. 只围绕正在交付的能力抽模块，不要求先把 `cli.ts` 缩到某个行数。

建议的逻辑边界包括 `runtime`、`providers`、`tools`、`context`、`sessions`、`commands`、`ui`。是否立刻重排目录不重要；每轮只提取一个行为边界，并使用回归测试保住契约。

关键取舍：

| 选择 | 推荐 | 原因 |
| --- | --- | --- |
| 重写 vs 增量 | 增量 | 避免丢失已有平台与权限处理 |
| 终端 vs 独立 GUI | 终端先成熟 | 当前用户与代码资产都在此 |
| 精简工具 vs 大量内置 | 稳定核心 + 可发现扩展 | 降低上下文与选择负担，但不能删除解决任务所需工具 |
| 自建 Agent 内核 vs 直接替换为 Pi | 先保留内核，借鉴接口 | 整体迁移的兼容、安全与授权成本尚未评估 |
| 提示词约束 vs 程序约束 | 两者各负其责 | 权限、状态与证据必须由程序执行 |
| 减少审批 vs 真实边界 | 精确授权并评估隔离后端 | 不能把放行更多 Shell 命令当作沙箱 |

操作系统/容器隔离值得做独立可行性验证，但不是首版所有工作都停下来的前置条件。若缺少可靠隔离，就继续准确暴露当前账户权限执行的限制，不宣传“安全无人值守”。

## 8. 分阶段路线与交付

以下按“一个主维护者 + AI 辅助开发、范围保持稳定”的投入假设估算。周期是规划区间，不是保证；阶段末依据实际反馈调整。版本号是建议，正式发版前查 Registry 并防止覆盖。

| 阶段 | 参考投入 | 主要交付 | 用户得到什么 |
| --- | --- | --- | --- |
| P0：收敛方向 | 1–2 个工作日 | 更新正式路线图、问题分级、保留旧结果、冻结首批范围 | 不再围绕旧评测反复停转 |
| P1：日常任务可用 | 1–2 周；建议 v0.18.0 | 中文反馈、错误/循环、可信验证、任务 diff 第一版、基础 /check | 修 bug 更顺、结果更清楚 |
| P2：理解与连续工作 | 2–3 周；建议 v0.19.0 | Provider 历史兼容、上下文按需、索引/patch 可靠性、插话与恢复一致性 | 跨文件任务和长会话更可靠 |
| P3：交付工作流 | 2–3 周；建议 v0.20.0 | /review、变更/验证整合、多包检查、首次使用与诊断收敛 | 能从需求走到可审查结果 |
| P4：可扩展候选版 | 2–4 周；建议 v0.21.x / 1.0 beta 候选 | 事件接口稳定，按反馈选一个集成方向，完善平台/发布 | 日常主力候选，不是功能全集 |

总量约 8–12 周（取决于范围和兼职投入）；复杂恢复、隔离和协议问题可拉长。每阶段可以形成内部构建，不要求每个小任务都发一个 npm 版本。

P1 范围较多，因此采用两次内部交付：先执行正确性和反馈，再任务改动视图与 `/check`；用户只对最终候选集中体验一次。

### P0：明确哪些旧规则被替换

批准后更新 ROADMAP 与根目录唯一当前设计稿：

- 从“先完成 30/60 次真实对照”调整为“先交付日常编码质量与体验”。
- 保留真实运行预算和危险操作确认；删除阶段间重复人工门禁。
- 原始结果保留，不把中断结果改成完成，不直接与新工具协议结果比较。
- 首版检查不扩到 20 道正式题，不追加新的 Provider、凭证后端和媒体功能。
- 已有个人评估文件不覆盖、不自动纳入提交。

### P1：第一批具体开发清单

| ID | 工作 | 主要代码落点 | 完成证据 |
| --- | --- | --- | --- |
| A1 | 结构化工具结果最小契约，兼容旧 string 工具 | types、tools、agent | 失败/取消/拒绝/成功结果离线回放一致 |
| A2 | 修复验证误判与验证过期，补最小模型结束状态 | tools、agent、providers、execution-report | 版本/帮助/echo 不算检查；改后旧通过失效；模型输出截断不能判为完成 |
| A3 | 同类失败与进展感知 | loop-guard、agent | 换参数失败能停止；有新证据时继续 |
| A4 | 中文分段反馈与交互草稿策略 | agent、cli、interactive-ui、language-output | 不漏秘密、不误标完成、不破坏输入 |
| A5 | 本任务/工作区变更视图 | checkpoint、change-summary、session | 预存改动、新文件、暂存变更、外部修改均正确区分或标未知 |
| A6 | /check 基础入口 | 新命令模块、现有 project_info/validate_project | 发现、执行、失败、取消和 Plan 只读 |
| A7 | 2–3 个产品入口离线场景 | test、scripts | 使用真实工具/检查进程，不依赖 eval_* 替身 |
| A8 | 文档与候选包 | README、USAGE、PUBLISHING、ROADMAP、CHANGELOG | 标准发布检查与简短用户体验单 |

若跨 Provider 历史兼容测试在 P1 复现严重日常故障，将其修复提前；不以赶新功能为由继续宣称切换可靠。

### P2：跨文件与长任务

围绕两类实际任务推进：更改公共接口并更新调用方；压缩/中断后继续完成原任务。

交付统一 Provider 消息、能力状态、上下文预算组成可见、按能力加载提示词、文件变化感知、指令作用域、会话搜索与标题、待回答状态恢复及恢复边界测试。用位于搜索/索引容量边界之外的目标文件测试覆盖提示及后续定位。先使用已有路由和索引；复杂自动路由和向量检索仍暂缓。

### P3：更容易交付和复查

新增只读 `/review` 工作流；完善 `/check` 包管理器与 monorepo 选择；完成摘要关联 task diff、检查证据和已知限制。整合首次配置与已有 update/web/provider 诊断，只有用户仍找不到入口时才增加总 `/doctor`。

选择少量真实用户，每周收集“为何退出或换回其他工具”的原因，按发生频率和影响排序修复。

### P4：根据使用反馈选择扩展

从以下方向中选一个主项，不同时做四个：

1. 编辑器用户多：稳定 JSON/RPC 最小接口，再做轻量 VS Code 集成。
2. 前端任务多：可选浏览器测试集成与截图反馈。
3. 大任务多：完善现有多 Agent worktree 调度与审查证据。
4. 团队自动化多：非交互执行、稳定退出码、结构化报告与 CI 接入。

1.0 命名应等待稳定性和用户使用证据，不由日历自动决定。沙箱、系统凭证库、远程执行和完整 SDK 是 3–6 个月内按需求展开的候选，尚未承诺全部完成。

## 9. 轻量但有效的验证方案

用户已经明确指出验收过于耗时。应改变验证的组织方式，而不是让用户承担同样多的步骤，也不是取消结果正确性的检查。

### 9.1 三层验证

| 层级 | 谁执行 | 触发 | 内容 |
| --- | --- | --- | --- |
| 改动级 | 开发自动完成 | 每个逻辑变更 | 对应单元/集成测试；用例覆盖实际失败路径 |
| 候选级 | 本地/CI 自动完成 | 同一候选提交 | 类型、全套测试、构建、包检查、安装与任务入口冒烟 |
| 体验级 | 用户集中体验 | 每个候选版本一次 | 2–3 个真实工作流，目标 10–15 分钟；复杂项目耗时另记 |

通过且代码未变的检查不反复执行。若最后又改动相关代码，则补相应检查；最终发布包必须对应已验证的提交。

### 9.2 小型产品场景集

先选 6–8 个代表场景，不建新的大型评测平台：

- 单文件修复与真实测试。
- 公共接口跨文件修改。
- 新增回归测试，能在缺陷版本上失败。
- 陌生模块问答，有正确文件与符号引用。
- 中途改变要求，目标更新正确。
- 压缩/重启后继续，不重放未知操作。
- 用户已有修改与新建文件的审查。
- 权限拒绝、取消和非零退出的诚实报告。

这些场景首先用于脚本化 Provider 回放，走产品工具与命令执行路径。真实模型只在修改核心策略、出现用户可复现问题或需要比较候选时选择相关场景；不是每次改文档都跑全部。

复现波动时才重复相同任务，保留所有结果；不通过筛掉失败样本展示成功率。

### 9.3 对照的两个问题要分开

- **框架对照：**能用相同模型/API/预算时，对比工具、上下文和运行行为；强调差异可归因的范围。
- **产品体验对照：**Claude Code、Codex、Pi 与 Xiu 各使用公开记录的配置，在相同仓库快照和任务上比较。模型不同则只能比较完整产品配置，不能把差异全部归因框架。

第一轮只是内部决策材料。没有固定环境、完整结果和足够样本，不发布“超越某产品”或“降低 40% Token”的宣传。

安全与恢复的局部回归是每次相关改动的正常工作；无需先开展一场全仓安全研究才能做普通功能。已核实的发布阻断问题必须修，未经证实的评估报告条目先复现再定级。

## 10. 判断产品是否变好的指标

北极星指标建议为：**无需用户修正 Xiu 自身操作错误即可完成，并得到用户接受的真实任务比例。** 需求本身需要讨论不算产品故障；用户被迫反复指出路径、命令和验证错误需要计入。

所有数字先作为建议目标，首轮采样后确定基线，不是当前成绩。

| 指标 | 记录方式 | 初期目标 |
| --- | --- | --- |
| 首次任务完成 | 少量新用户操作记录 | 有可用模型与环境时，大部分人 10 分钟内完成小任务 |
| 任务被接受 | 记录接受/部分完成/失败及原因 | 目标场景稳定改善，不用挑成功任务凑比例 |
| 用户纠错次数 | 按次记录框架导致的干预 | 中位数下降；简单任务争取无需操作级纠正 |
| 交互反馈 | 区分客户端反馈、模型首字、总耗时 | 本地接收反馈争取 <200ms；取消状态反馈 <1s，均需在约定机器测量 |
| 空转与重复失败 | 同因失败次数、预算耗尽情况 | 确定性回归用例中均有界退出，不能靠增加预算掩盖 |
| 完成误报 | 检查失败/未执行却显示通过 | 自动回归中为零；线上问题立即优先处理 |
| 改动可理解 | 本任务/原有改动/来源未知 | 不遗漏新文件，不错误认领用户改动 |
| 长会话连续性 | 压缩前后目标与证据比对 | 测试中的必保字段完整，真实失败转回归 |
| 使用意愿 | 试用者一周后是否主动继续用 | 先找 5–10 人；持续使用比下载量更重要 |

默认不新增遥测。维护者可手工记录自己的使用问题，外部用户按意愿提供脱敏报告。需要收集使用数据时另行设计告知、范围和关闭方式。

## 11. 投入、费用与工作节奏

资源分配建议：约 50% 核心质量与上下文，25% 交互及交付流程，15% 自动回归和发布，10% 文档与用户反馈。比例用于防止方向失衡，不逐小时追踪。

每周一个主题，每批功能有可运行交付。问题优先级：

1. 数据丢失、凭证暴露、错误执行与结果误报。
2. 高频任务失败、长时间空转、取消/恢复不一致。
3. 高频交互摩擦、缺乏必要上下文、diff 不清楚。
4. 新工作流和扩展。
5. 低频外观、更多配置和更多 Provider。

不根据过往发布速度承诺每周一个正式版本。优先“稳定候选→集中体验→有需要再发布”。

模型费用需要执行时以实际价格和 Token 用量核算。历史 100 USD 上限和确认码属于原评测配置，不自动授权新模型、新端点或新一轮收费测试。本稿不消费该预算；后续需要真实调用时，把配置、范围和总上限一次说清，不让用户为同一已批准范围反复确认。

成本优化看“每个被接受任务的总成本和时间”，同时记录输入、输出、重试与有效缓存；便宜模型反复失败也有用户时间成本。

## 12. 兼容、发布与恢复策略

- 保留已发布 CLI 行为，新增入口尽量兼容；变化明确写入 CHANGELOG。
- 会话和任务记录有模式版本；新字段可兼容读取，必要迁移可回退，未知版本不得误解释后执行。
- 不覆盖 npm 已发布版本；发布前核对 Registry，版本与 tag 指向精确提交。
- 根目录只保留当前版本设计，已完成历史留在 Git 和路线图摘要。
- README、中文使用说明、发布说明和路线图同步，不把计划能力写成已上线。
- 先在 Windows 主路径验证新增行为，CI 继续三平台；跨平台体验问题单独跟踪，不把 CI 通过等同全部平台成熟。
- 新能力可用明确设置或内部适配器逐步启用；不能静默降级关键权限或把失败隐藏成成功。
- 命令行脚本使用退出码和结构化结果，不能依赖抓取彩色终端文本。

## 13. 风险与应对

| 风险 | 对产品的影响 | 应对 |
| --- | --- | --- |
| 底层模型达不到目标任务要求 | 优化框架后仍反复失败 | 分离模型与框架对照，允许用户选择合适配置 |
| 结构化结果迁移影响太多模块 | 版本迟迟不能交付 | 加兼容层，先执行/编辑/检查三条高频路径 |
| 流式输出破坏门禁或脱敏 | 显示错误完成或泄漏 | 草稿与状态分离，测试跨 chunk 脱敏和取消 |
| diff 归因错误 | 用户误审查或覆盖自己的改动 | 保存起点、识别外部修改、来源不明就明示 |
| 为减少审批放宽执行 | 风险超出用户预期 | 精确许可与程序边界，未隔离时准确说明限制 |
| 评测再次成为主项目 | 长期没有产品改善 | 限定小场景、复用产品路径、按变化触发 |
| 工具/模型升级破坏兼容 | 切换或恢复失败 | 版本化适配器、离线协议回放、失败可解释 |
| 同时开发 GUI/浏览器/团队平台 | 稀释核心投入 | P4 只选一条，其他进入后备清单 |
| 没有真实使用反馈 | 优化维护者想象中的问题 | 从 P1 候选开始招募试用，不等所有功能齐全 |

## 14. 暂不做与有条件再做

近期不做自研基础模型、全套 IDE、独立桌面壳、插件商城、团队计费系统、全面远程计算平台或自动部署发布。也不承诺任意 Shell 修改都能撤销。

以下并非永久排除：

- 原生沙箱：当需要更强自主执行时，以明确平台支持和降级规则专项推进。
- 系统凭证库：根据真实 macOS/Linux 用户需求与环境验证安排。
- 浏览器：先做可选前端验证集成，再决定是否产品化。
- 语音、媒体和数据处理：保留已有能力，近期不占据编码主线。
- 新语言智能：出现真实需求后增加语言适配，先保证通用读取/搜索/运行不受阻。
- 更大评测集：核心工作流稳定、需要公开质量论据后再扩。

## 15. 审核与下一步

本计划建议你重点确认三件事：

1. **定位：**先做中文/Windows/自选模型的日常编码体验，并以通用工具质量为长期目标。
2. **首批范围：**P0 + P1；Provider 严重兼容问题若复现则提前修复；不把整个半年路线一次性实施。
